## 순서를 정한 이유

v0.1에서는 "백테스트가 통과해야 UI를 만든다"였다. 지금은 다르다.

**이 앱에는 전략이 맞든 틀리든 즉시 가치가 있는 부분이 있다** — 청산가 거리, 손절 주문 누락 경고, 이벤트 임박 알림, 세션 레짐 표시. 이건 예측이 아니라 사실 조회라서 검증할 것도 없다. 그리고 10배 레버리지에서 실제로 계좌를 지키는 건 이쪽이다.

그래서 **안전장치를 먼저 만들어 바로 쓰기 시작하고, 전략과 AI는 그 위에 얹는다.**

```
Phase 0    데이터 수집            ─┐
Phase 1    세션·이벤트 게이트       │
Phase 1.5  이벤트 자동 수집         ├─ 여기까지가 "언제 손대면 안 되는지"
Phase 2    리스크 엔진 + 계정 연동 ─┘   (신호 없이 경고만으로도 가치)
Phase 3    전략 엔진
Phase 4    백테스트 검증  ⭐ 게이트  ← 여기서 통과 못 하면 신호 기능은 안 낸다
Phase 5    실시간 대시보드 (웹)
Phase 6    AI 파이프라인
Phase 7    앱
```

## Phase 1.5 — 이벤트 자동 수집 ✅ 구현 완료

### 왜 필요한가

지금은 `data/events.yaml`에 직접 날짜를 적어야 한다. **손으로 적는 방식은 언젠가 반드시
빠뜨리고, 빠뜨린 날이 하필 청산되는 날이다.** NVDA 실적일 하나를 놓치면 SOXL이
10~20% 움직이는 밤에 게이트가 아무 경고도 못 한다. 이건 편의 문제가 아니라 안전 문제다.

### 소스 (전부 무료 · 조사 완료)

| 이벤트 | 소스 | 확인된 사실 | 제약 |
|---|---|---|---|
| **경제지표 일정** | **FRED** `/fred/releases/dates` | 무료 API 키. `include_release_dates_with_no_data=true` 로 **미래 발표일** 조회 가능. 공식 소스라 신뢰도 최상 | **날짜만 주고 시각을 안 준다** → 아래 매핑 필요 |
| **실적 발표일** | yfinance (이미 설치됨) | 키 불필요 | 발표 시각이 BMO/AMC 수준으로만 나올 수 있음. 날짜가 자주 변경됨 |
| 실적 (대안) | Finnhub `/calendar/earnings` | 무료 티어 존재 (요금제 확인 필요) | 키 필요 |
| FOMC | 연준 공식 일정 | 이미 반영됨 | 연 1회 갱신 |

**FRED가 시각을 안 주는 문제**는 미국 지표 발표 시각이 사실상 고정이라 매핑표로 해결한다.

```
BLS·BEA·Census 계열 (CPI, PPI, 고용상황, 소매판매, GDP, PCE)  → 08:30 ET
ISM · 컨퍼런스보드 · JOLTS (제조업/서비스 PMI, 소비자신뢰)      → 10:00 ET
```

### 설계

```
src/th/sessions/sources/
├─ base.py        EventSource 프로토콜:  fetch(start, end) -> list[Event]
├─ manual.py      data/events.yaml       ← 항상 최우선 (오버라이드)
├─ fred.py        경제지표 발표일 + 시각 매핑 + 중요도 화이트리스트
├─ earnings.py    SOXX 상위 10종목 실적일
└─ merge.py       중복 제거 · 우선순위 병합
```

- **병합 우선순위: 수동 > FRED > 실적 소스.** 손으로 적은 것은 절대 덮어쓰지 않는다.
- 수집 결과는 **DB `calendar_events` 테이블에 저장**한다(`03` 문서 7절에 이미 설계됨).
  그래야 소스가 죽거나 오프라인이어도 마지막 스냅샷으로 게이트가 계속 돈다.
- 갱신: `th calendar sync` 수동 + 하루 1회 자동(장 시작 전). 실적일은 자주 바뀌므로 매일.
- **신선도 표시**: 마지막 동기화가 24시간을 넘으면 대시보드에 "이벤트 정보 오래됨" 경고.
  조용히 낡은 일정으로 도는 것이 가장 위험하다.

있게 만들고 ② **수동 입력 경로(`events.yaml`)를 영구히 남긴다.** 자동화는 편의이지
의존 대상이 아니다.

| 1 | 78칸 중 50칸이 "거래량이 평소의 5~30%" | `bars_5m[-1]` 이 **아직 안 닫힌 묶음**(1~4분치)이었다. 그 거래량을 완성된 5분봉 중앙값과 비교했다 | `resample(..., drop_incomplete=True)` — 미완성 묶음을 버린다. 지표는 닫힌 봉으로만 |

덤으로 하나 더: `load_bars` 가 `ts <= at` 이라 **형성 중인 1분봉**이 섞여 최대 59초를

### `th funnel` 실측 결과와 그에 따른 수정 (2026-09-08)

5,850번 평가의 사망 지점:

| 단계 | 죽음 | 남음 |
|---|---|---|
| 세션 게이트 | 654 | 5,196 |
| 시장 상태 필터 | 750 (유동성 456 · 변동성 288) | 4,446 |
| 셋업 필수 조건 | 3,873 | 573 |
| **리스크·점수** | **562 (그중 91%가 '4R이 너무 멂')** | **11** |

**병목은 셋업이 아니라 손절폭이었다.** 두 가지 원인이 겹쳐 있었다.

**원인 1 — 클램프와 발행 조건이 어긋나 있었다.**

```
손절 클램프 : [0.30%, 0.70%]      ← 5.2
발행 허용   : [0.40%, 0.625%]     ← 5.3 을 풀면 나오는 범위
죽은 구간   : 0.30~0.40% 와 0.625~0.70%
```

클램프를 통과한 손절이 발행에서 거부된다. 실측에서 **구조를 빼고 ATR 만 써도 손절
중앙값이 0.700%** (= 클램프 천장) 였으니 절반 이상이 자동 탈락이었다.

**원인 2 — 구조 탐색 창 60봉이 근거 없는 숫자였다.**

| 창(1분봉) | 손절 중앙값 | 발행 구간 안 |
|---|---|---|
| 10 | 0.700% | 25.0% |
| **15** | 0.700% | 21.6% |
| 20 | 0.700% | 17.3% |
| 30 | 1.219% | 9.9% |
| 60 (당시 값) | 1.380% | 8.7% |

#### 수정 — 숫자를 최대화하지 않고 원칙에서 파생시켰다

| 상수 | 전 | 후 | 근거 |
|---|---|---|---|
| `SWING_WINDOW` | 60 | **15** | S1 의 정의가 "최근 3개의 5분봉(=15분) 안의 되돌림"이다. 셋업이 틀렸다고 판정되는 지점은 그 되돌림의 저점이지 한 시간 전 피벗이 아니다. **표에서 10봉이 더 많이 나오지만 15를 쓴다** |
| `SL_MIN_PCT` | 0.30 | **0.50** | TP1 = 2R ≥ 본주 1% |
| `SL_MAX_PCT` | 0.70 | **1.00** | TP1 = 2R ≤ 본주 2% |
| `TP1_MIN_PCT` | 0.8 | **2 × SL_MIN** | 클램프에서 파생 (더 이상 독립 숫자가 아니다) |
| `TP2_MAX_PCT` | 2.5 | **4 × SL_MAX** | 클램프에서 파생 |

손절 범위 [0.50%, 1.00%] 는 **사용자가 처음부터 말한 목표**(본주 1~2% = 포지션
10~20%)를 TP1 = 2R 에 대입해 역산한 값이다. 오히려 기존 [0.40, 0.625] 는 TP1 을
0.8~1.25% 로 만들어 **사용자 목표보다 낮게** 잡고 있었다.

두 개의 테스트로 고정했다.

- `test_publish_band_matches_the_stop_clamp` — 죽은 구간이 다시 생기면 실패
- `test_any_atr_only_stop_is_publishable` — 구조가 개입하지 않으면 어떤 변동성에서도 발행 가능

> **이건 신호를 늘리려고 푼 게 아니다.** 판단 기준: ① 근거가 결과와 무관하게
> 성립하는가 ② 표를 보기 전에 정한 값인가 ③ 바꾼 뒤 판정을 out-of-sample 로만
> 하는가. 셋 다 만족한다. 15봉은 표에서 최대값이 아니고, 손절 하한은 오히려
> 0.30% → 0.50% 로 **더 보수적으로** 갔다.



### 수정 후 첫 결과 — 그리고 경계 버그 하나 더

### 1초 갱신을 하면서 API 호출을 안 늘리는 방법

비용이 다른 것을 분리했다.

| 무엇 | 주기 | 비용 |
|---|---|---|
| 가격·호가 | **1초** | DB 만 읽는다 (`th stream` 이 적재) |
| 계정·포지션·경고 | 3초 | 바이낸스 API |
| 시장 통계 | 20초 | 무거운 집계 |
| 당일 손익 | 30초 | income 조회는 가중치가 크다 |

**평가손익·카운트다운·경과시간은 브라우저가 매초 스스로 계산한다.**
서버는 진입가·손절가만 내려주고, R 계산은 화면에서 한다. 그래서 1초마다
숫자가 살아 움직이면서도 바이낸스 호출은 3초에 한 번뿐이다.

### 지킨 규칙 (테스트로 고정)

- 외부 리소스 0 — CDN 없음. 차트도 canvas 로 직접 그린다
- 계산은 전부 서버 — 브라우저에 지표 계산 함수가 생기면 테스트 실패
- **빈 사유 목록을 초록불로 그리지 않는다** — `is_permission_to_trade` 는 항상 false
- **조회 실패를 '포지션 없음'으로 그리지 않는다** — 마지막 값 + '오래됨' 표시
- 터미널과 웹이 같은 함수를 쓴다 (`no_trade_reasons`, `carry_forward`)

## Phase 6 — AI 파이프라인 (2.5주)

- [ ] k-NN: 벡터 구성 → FAISS 인덱스 → 중복 윈도우 제거 → 시나리오 A
- [ ] LightGBM: 삼중 배리어 라벨링 → 피처 40종 → **Purged Walk-Forward** → isotonic 보정 → 시나리오 B

**미통과 모듈은 UI에서 내린다.** 특히 "판단 보류"가 실제로 나쁜 거래를 걸러냈는지 확인 전에는 신호 차단에 쓰지 않는다.

## 실전 투입 전 마지막 관문

Phase 4를 통과했더라도, **최소 4주간은 신호를 보되 그대로 따라 하지 않는다.**

- 신호가 뜰 때마다 `signals` 테이블에 기록되고, `signal_outcomes` 배치가 사후 결과를 채운다
- 4주 뒤 **표시 승률 vs 실제 승률**을 비교한다
- 괴리가 10%p를 넘으면 백테스트가 현실과 다르다는 뜻이므로 Phase 4로 돌아간다

10배 레버리지에서 검증 안 된 신호를 따라가는 건 백테스트를 아예 안 한 것보다 나쁠 수 있다. 숫자가 붙어 있으면 사람은 더 크게 베팅하기 때문이다.
